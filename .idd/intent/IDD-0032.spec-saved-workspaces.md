# IDD-0032.spec-saved-workspaces

## Intent

Register and reuse named server-side working directories across Chat, interactive workflows, and manually launched headless Saved Agents.

## Related Specifications

IDD-0001, IDD-0023, IDD-0024, IDD-0025, IDD-0027, IDD-0028, IDD-0030, IDD-0031.

## Behavior

- A saved workspace has an application-assigned nonempty ID, required trimmed case-insensitively unique name, and an existing, absolute, normalized, unique directory path. Created/updated timestamps and a revision support optimistic concurrency. Users can create, rename, edit and remove definitions; removing a definition never deletes its physical directory.
- The existing picker offers named saved workspaces alongside browsing, direct paths and creating a child directory under WorkspacesRoot. Saving a directory is optional. Missing directories remain registered but cannot be launched until repaired.
- A launch selects either saved ID, direct path, or no workspace. Both ID and path simultaneously are invalid. Unknown IDs, malformed or inaccessible paths fail with an error, never a default fallback.
- The selection is resolved immediately before starting a root execution to one validated immutable path snapshot. Changing or deleting the saved definition after launch affects only subsequent root executions; filesystem contents themselves are not snapshotted.
- An active Chat conversation cannot switch workspaces after it has started. All participants in a root workflow share the same effective directory, but independent LLM context, approvals and runtime state. Separate root executions own separate sandboxes.
- Saved Chats retain the resolved path in their existing snapshot and restore from that path, never re-resolve a live saved ID. Direct-path launches and old chats remain compatible.
- Scheduled Agent bindings optionally reference a saved workspace ID. Broken references are retained and produce safe Run Now failures. Changing the binding does not affect Quartz scheduling, which remains diagnostic-only.
- A saved workspace is not authorization. Headless text-only runs can receive the path; read-only File Access requires an explicit read-only profile with read approval disabled. Native Skills use existing discovery and tool policy; read-only skill tool approvals must be narrowly scoped. Shell, script execution, unsupported capabilities and unexpected approvals fail closed.

## Durable Architecture And Constraints

- Saved definitions are configuration only, not runtime sessions, sandbox instances, approval grants or conversation state.
- Catalog changes use atomic in-process read-modify-write with expected revision checks. A missing file means an empty catalog; corrupt or structurally invalid JSON is never silently replaced. Catalog reads do not create directories.
- New saved paths must be fully qualified and exist at registration; normalization and comparisons follow host platform path rules. Filesystem aliases are not guaranteed to deduplicate. Existing directories outside WorkspacesRoot may be saved. Availability is checked again before launch and tools must independently enforce filesystem boundaries.
- The common application resolver determines location, not necessity of tools or model function calling. Relative and Claude Skills sources need a workspace. Discovered native Skills need function calling for progressive disclosure independently of path validation.
- Runtime receives the existing WorkspacePath snapshot. Each headless run uses its own noninteractive approval coordinator, runtime resources and capability allowlist, without inherited interactive approvals.

## Non-Goals

New Project entity, Git/worktrees, global default workspace, automatic scheduled agent execution, headless workflows, persistent run history, alternate filesystem engines, automatic RAG indexing or installing Skills, full file manager, multi-process transactions, or deleting on-disk files.

## Acceptance Criteria

- Catalog CRUD persists with unique names/paths, validation, revision conflicts, safe corruption handling and no physical deletion.
- Both saved and direct workspace choices launch Chat and workflows with one path for validation and runtime.
- Old Saved Chats restore original path snapshots despite changes to saved definitions.
- Scheduled Task Run Now resolves workspace references safely without modifying Quartz or regular Chat.
- Headless read-only File Access and safe native Skills can use the selected workspace without enabling write, shell or script execution; unsupported capabilities fail closed.

## Verification

Automated tests cover catalog concurrency, JSON integrity, strict resolution and snapshot semantics, interactive/workflow integration, scheduled binding, read-only headless capability policy and negative cases. Manual end-to-end tests cover reading a workspace file in Chat, workflows and Run Now, and retaining files after removing a saved definition.
