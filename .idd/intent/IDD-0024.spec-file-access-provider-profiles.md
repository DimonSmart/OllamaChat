# IDD-0024.spec-file-access-provider-profiles

## Intent

Let users manage reusable File Access Provider policies for direct saved-agent conversations.

## Related Specifications

Related: IDD-0001, IDD-0005, IDD-0020, IDD-0023.

## Behavior

Users can create, edit, and delete named File Access Provider profiles. A profile defines optional provider instructions, read-only or read-write access, and whether read and write operations require approval. Empty instructions use framework defaults. In read-only mode, write approval is not configurable because write operations are unavailable. A saved agent may select one profile, but neither an agent nor a profile stores a workspace path.

Each direct conversation supplies one existing local directory as its current workspace. The agent sees only paths relative to that workspace. Changing the workspace between runs preserves the direct agent session and its state; changes never affect a saved profile or agent and are not remembered for future conversations. Profile edits apply to new conversations only.

A File Access-enabled direct agent can launch only with an effective model that supports function calling. If the selected model lacks that capability, launch validation explains that File Access requires function calling and prevents the conversation from starting.

## Durable Architecture And Constraints

Profiles are application-owned persisted models expressed in user-facing positive policy terms. The runtime maps the profile to the native Microsoft Agent Framework File Access Provider and delegates filesystem boundary enforcement to the framework's filesystem store. File access is not enabled for workflows, attachments are independent of the workspace, and the UI controls only workspace binding and approval decisions rather than file operations.

## Non-Goals

This capability does not provide workspace persistence, recent folders, a file browser or editor, attachment import, multiple roots, remote filesystems, filesystem watching, File Memory, Shell Environment, or workflow file access.

## Acceptance Criteria

- Profile names are required and unique without regard to case.
- Profiles expose instructions, read-only/read-write access, and approval requirements; read-only profiles do not expose write tools.
- The profiles catalog is available from main navigation near reusable agent configuration, and deletion requires confirmation.
- Saved-agent configuration offers the available profiles plus no selection and never offers a filesystem-path field.
- A File Access-enabled direct conversation requires an existing workspace directory and displays its normalized path in session state.
- A File Access-enabled direct conversation can launch only when its effective model supports function calling; agents without File Access remain eligible to launch on models without that capability.
- Workspace changes are allowed only between runs, preserve the same session state, and take effect for subsequent file operations.
- File Access approval integrates with the ordinary approval UI but never offers standing approval.

## Verification

Automated coverage verifies profile CRUD, policy mapping, saved-agent propagation, workspace and function-calling launch validation, read-only tool availability, workspace boundary and switching behavior, same-session preservation, approval behavior, and rejection of unsafe workspace changes. Manual verification confirms profile administration, starting an agent against a workspace, read/write approval, and switching between two workspaces.
