# IDD-0025.spec-sandbox-profiles

## Intent

Let users manage reusable sandbox profiles and run shell-enabled agents and workflows inside an isolated session-owned execution environment.

## Related Specifications

Related: IDD-0001, IDD-0003, IDD-0005, IDD-0020, IDD-0023, IDD-0024.

## Behavior

Users can create, edit, and delete named sandbox profiles. A profile stores a provider type and provider-specific YAML configuration in one editable text field. The profiles catalog lists each profile's name, provider type, and provider-provided summary values such as image, limits, and network mode. Invalid provider selections, empty configuration, malformed YAML, unknown YAML properties, and provider-specific validation failures block save with a user-readable error.

A saved agent may explicitly opt in to shell execution. Launching a shell-enabled direct agent requires both an existing workspace directory and a selected sandbox profile. Launching a workflow requires the same resources when any reachable participant is shell-enabled, and one root workflow session shares one sandbox instance across all of its shell-enabled participants. A sandbox profile selection never becomes part of the saved agent or workflow definition; it is always a launch-time session resource.

The session workspace is shared between File Access and sandbox-backed shell execution. The host workspace is mounted inside the sandbox at `/workspace`, and shell commands start from that directory. File changes made through shell execution are immediately visible to File Access and vice versa. A sandbox-backed session keeps one persistent sandbox instance for its lifetime, reuses it across turns, and destroys it on reset or launch failure cleanup. Starting a root chat session is a single-flight operation: one launch attempt creates no more than one sandbox instance, and a repeated launch request while initialization is in progress does not create additional runtime resources. Shell commands continue to use the existing approval flow and never fall back to host execution when sandbox creation or availability checks fail.

During sandbox-backed launch, the launch UI prevents changes to the selected agent or workflow, runtime inputs, MCP bindings, workspace, and sandbox profile. It shows an indeterminate progress indicator with the current long-running startup stage instead of a fabricated percentage. If startup fails, the launch form returns to an editable state for a corrected retry and displays the diagnostic failure message while the full exception is logged.

The first registered provider type is Docker. Docker-backed profiles define a container image, network mode, CPU limit, memory limit, process limit, per-command timeout, output cap, container user, and whether the root filesystem is read-only. The default seeded profile is named `.NET 10 Small`, uses an Ubuntu-based .NET 10 SDK image, uses Docker bridge networking so shell tasks can restore NuGet packages, and runs as an unprivileged container user. The runtime redirects the container home, .NET CLI state, and NuGet package cache into writable directories under `/workspace`, allowing package restore while the container root filesystem remains read-only. Existing untouched instances of the former network-disabled seed profile are upgraded to this configuration, while customized profiles are preserved.

## Durable Architecture And Constraints

Sandbox profiles are application-owned persisted models, while sandbox instances are per-session runtime resources. Provider discovery is registry-based and provider-agnostic in the UI and launch flow: adding another provider must not require switching on provider type in saved-agent configuration, session launch UI, workflow runtime, or sandbox-profile CRUD composition. Provider-specific parsing, validation, summary generation, availability checks, and runtime creation belong to the provider implementation.

One sandbox instance belongs to exactly one root chat session. Persistent shell state, mounted workspace contents, and tool-visible side effects are therefore scoped to one direct conversation or one root workflow conversation and must not be shared across users, sessions, or concurrent conversations. Workflow participants that share a sandbox must serialize shell execution through that single instance.

## Non-Goals

This capability does not provide image building, Docker Compose, multiple sandboxes per session, arbitrary volume mounts, arbitrary container runtime arguments, dynamic sandbox reconfiguration during a session, workspace switching during a sandbox-backed session, container persistence across application restarts, remote sandbox providers in the first release, or claims of absolute isolation against all attacks.

## Acceptance Criteria

- Sandbox profiles expose required unique names, provider type, YAML configuration, timestamps, and provider-derived summary fields.
- The sandbox profiles catalog is available from main navigation near reusable agent configuration, and deletion requires confirmation.
- Provider-specific validation blocks invalid YAML, unknown properties, unsupported provider types, and unsafe or out-of-range settings with user-readable errors.
- The application seeds one `.NET 10 Small` Docker profile with bridge networking and upgrades only an untouched legacy default profile without duplicating it or overwriting customized profile configuration.
- The Docker runtime maps .NET CLI state and NuGet package storage to writable paths below `/workspace` when the container runs as an unprivileged user with a read-only root filesystem.
- Saved-agent configuration exposes explicit shell enablement that defaults to off and persists with the template.
- Starting a shell-enabled agent or workflow requires an existing workspace directory, a selected sandbox profile, and a model that supports function calling.
- Starting a non-shell-enabled agent does not require a sandbox profile.
- A shell-enabled root session creates exactly one sandbox instance, reuses it across turns, and disposes it on reset, new chat, or startup failure cleanup.
- Root chat session startup is single-flight; repeated startup requests during initialization are rejected or ignored without allocating another sandbox or agent session.
- Sandbox-backed launch UI reports the current startup stage with indeterminate progress and restores editable launch controls after startup failure.
- Shell commands execute inside the sandbox rather than on the host, start in `/workspace`, and require approval through the ordinary modal approval UI. Approval for the current session permits subsequent sandbox shell commands only within that chat session.
- Sandbox-backed sessions project sandbox state in session UI and do not offer mutable workspace editing while the sandbox is active.
- Workflow participants that are shell-enabled share one sandbox instance and do not execute shell commands concurrently against the same persistent shell.
- Adding a new sandbox provider requires only provider-specific model and runtime implementations plus registration.

## Verification

Automated coverage verifies sandbox profile CRUD, provider registry behavior, YAML parsing and validation, provider summary generation, launch validation for direct agents and workflows, shell enablement propagation, sandbox lifecycle cleanup, session-wide shell approval reset with the chat session, shared-workspace visibility with File Access, single-sandbox workflow reuse, single-flight startup rejection, retry after startup failure, and serialized shell execution. Provider-level automated coverage verifies Docker option mapping, bounded output, timeout behavior, security-related defaults, the bridge-network default required for NuGet restore, writable .NET and NuGet cache paths, and seeded-profile idempotency without requiring Docker for ordinary unit tests. Optional Docker integration coverage verifies container startup, command execution, host-visible workspace mutation, launch-stage visibility during long sandbox initialization, and container removal only when explicitly enabled.
