# IDD-0030.spec-scheduled-tasks

## Intent

OllamaChat users can define reliable, local, scheduled timers that report when they fire and optionally attach Saved Agents for manual headless execution. Scheduled firing is diagnostic only.

## Related Specifications

- IDD-0023: Compact shared user interface.
- IDD-0029: Development startup and application lifetime.
- IDD-0020: C#/.NET architecture.
- IDD-0031: Manual headless Saved Agent execution.

## Behavior

- The Scheduled Tasks management page allows creating, finding, editing, disabling, enabling and deleting named timers, with visible operational state and recoverable synchronization errors.
- A timer may optionally reference a Saved Agent and prompt. Users can run it manually irrespective of the timer Enabled state, subject to launch validation and one global active run. Manual run state is separate from Quartz status.
- Supported schedules are intervals of whole minutes or hours, daily times, selected weekdays, selected month days and native Quartz Cron with minute resolution.
- Each timer uses a selectable time zone. Calendar schedules follow the time-zone's daylight saving rules, while intervals represent absolute elapsed durations.
- The editor previews up to five upcoming times without altering an active timer. An inactive timer is previewable, and an exhausted calendar schedule can be stored while disabled.
- Definitions, including desired Enabled state, survive application restart. Actual firing times, active state and errors are runtime information and reset with the process.
- Enabled schedules are restored upon host startup. Missed periods do not cause catch-up execution. Quartz firings only update diagnostics and runtime state; they cannot invoke agents, workflows, LLMs, MCP tools or arbitrary user code.
- A timer only appears Active after Quartz confirms registration; errors and exhausted schedules remain distinguishable from user-disabled timers.
- Each accepted diagnostic Quartz firing emits one in-process event with its timer ID, name at acceptance, and actual UTC firing time. Every active interactive Blazor circuit displays `Timer fired: {TimerName}` through the global informational Snackbar, including repeated identical messages.
- The Scheduled Tasks page refreshes last/next firing diagnostics after a firing event, local CRUD actions, or manual Reload; there is no periodic polling. Event refresh does not change the open editor or its preview.

## Durable Architecture And Constraints

- The host owns a single Quartz.NET RAM scheduler, independent of any Blazor page/circuit. Timers cannot fire when the ASP.NET Core host is stopped.
- The JSON file in the application's user storage root is the authoritative definition store. Writes are atomic replacement operations and serialized with their read/modify/write cycles. Revision checks reject stale edits.
- Saving desired state precedes reconciling Quartz. A failed save must not alter the running schedule; a failed reconciliation must remain visible and retryable.
- A diagnostic job checks current desired state and a schedule generation before acknowledging a firing, preventing removed or disabled timers from being accepted after a stale trigger fires.
- In-process scheduler synchronization is repeatable and never creates multiple jobs for one timer ID. Individual invalid definitions do not obstruct valid timers.
- An unreadable document is not silently replaced by an empty one; timer modifications are blocked until the document can be read.
- Scheduling definitions contain no runtime Quartz objects; an optional Saved Agent reference and prompt are metadata and do not change the trigger or interval anchor.
- The timer JSON stores only the Saved Agent binding, not manual execution status, transcript, result or run ID.
- Existing packaged auto-shutdown and development host lifetime remain unchanged.
- A singleton synchronous in-process publisher is independent of Quartz and UI. It stores no history, isolates each subscriber's synchronous exceptions, and is invoked only after runtime acceptance and release of the runtime gate.
- Interactive layouts and the Scheduled Tasks page independently subscribe/unsubscribe during their component lifetimes. Notifications are best-effort for active circuits, with UI calls dispatched to Blazor and asynchronous errors locally observed. Page refreshes are single-flight with a dirty flag to prevent stale concurrent updates.

## Non-Goals

- Automatic agent/workflow launch on a timer firing, persisted manual-run history, missed-event replay, multi-process scheduling and execution after host shutdown.

## Acceptance Criteria

- All supported schedules can be created, previewed and edited using compact shared management UI patterns.
- A weekday 14:00 timer in Europe/Madrid follows that local time across DST transitions.
- An unchanged interval schedule is not restarted by a metadata or Saved Agent binding edit.
- Restart restores enabled registrations without compensating for times missed while the host was stopped.
- The user can inspect last/next firings and distinguish Disabled, Active, Completed and Error.
- Invalid stored records are retained for repair, not activated; damaged JSON is never overwritten implicitly.
- No Quartz firing triggers agent or workflow execution. An explicitly requested Run Now may start a Saved Agent as defined by IDD-0031.
- Every accepted job invocation publishes exactly one event even if LastFiredUtc did not change, whereas rejected, removed, disabled or stale-generation jobs publish none.
- Global Snackbar shows one notification per accepted firing in every active interactive circuit, including repeated identical names. The Scheduled Tasks page only refreshes diagnostics and never adds a second Snackbar.
- The page has no five-second polling; event updates preserve the current editor and avoid stale competing reads.

## Verification

Exercise schedule parsing, DST, preview, CRUD/revision conflicts, atomic persistence, runtime registration, restore, error isolation and stale-job filtering; verify the page and existing startup behavior. Test publisher delivery, subscriber exception isolation, duplicates and concurrency, as well as job acceptance and publication outside the runtime gate. Manually verify Snackbar notifications across pages, repeated names, multiple circuits, navigation/disposal, editor preservation, and diagnostics refresh.

## Saved workspace binding

An optional Saved Workspace ID belongs to the Agent Execution binding and is resolved only for manual Run Now execution (IDD-0032). Changing or deleting this binding does not recreate Quartz triggers or reset interval anchors. A deleted or inaccessible workspace is a persistent configuration error for manual execution, not a reason to delete, disable or rewrite a timer. Automatic agent execution remains excluded.
