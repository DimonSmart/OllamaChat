# IDD-0033.spec-interactive-steering

## Intent

Allow a user to provide a text instruction to an already executing direct Saved Agent, without stopping its current generation or tool call and without starting another independent agent run.

## Related Specifications

Related: IDD-0001, IDD-0005, IDD-0023, IDD-0026, IDD-0028, IDD-0020.

## Behavior

While an interactive direct Saved Agent is executing, the composer remains editable and offers a compact **Steer** action alongside the existing **Stop**. Ctrl+Enter sends Steering while this run is active and supported; otherwise it sends an ordinary message only when idle. Workflows, headless/scheduled agents, and individual Background Agents are not Steering destinations.

Steering is text-only. If attachments are selected, the Steer action is unavailable and the attachments remain intact. Invalid, stale, empty, too-long or over-limit submissions do not clear the composer and do not create a transcript entry. A successfully accepted submission clears only the typed text; it does not prevent Stop.

Each accepted instruction is recorded as a distinct user message with an immutable steering ID, originating run ID, submission time, order and visible delivery status. `Pending` indicates queue admission only, `Delivered` indicates that a subsequent actual root-model request contained the user-role message, and `Not delivered` indicates the run ended before acknowledged delivery. Delivered is not an indication of compliance by the model. Terminal statuses are retained during navigation, in transcript export and in the Saved Chat document.

During an active tool call, delivery occurs at the next model request. During a final response with no actionable tool call, the native Framework injector can make an extra model call inside the same run to process a timely Steering message (variant B). Stop/Cancel and tool approval keep their current semantics. Steering is unavailable during either form of pending Tool Approval and cannot bypass an approval gate. A run that has already finished cannot be resumed via Steering.

Submission limits: 4,096 characters per message, at most 8 pending instructions, and no more than 16,384 pending characters. Distinct accepted messages preserve their order; a repeated submission identifier is idempotent for the active run.

## Architecture and Constraints

The application's root Harness runtime uses the native MAF `MessageInjectingChatClient` and existing per-service-call history persistence. It does not create a second `RunStreamingAsync`, inject privileged instructions, or change the agent loop. Delivery is observed only at the actual root `IChatClient` boundary. Additional steering metadata is backward-compatible with the existing Saved Chat format v3.

**Known Framework limitation, accepted for UI testing:** MAF 1.27/1.28 exposes enqueue and pending snapshot but no safe public removal of individual pending native messages. A Steering enqueue racing with the final queue check can leave a stale message that the next run consumes even though its transcript status was `Not delivered`. The technical evidence and regression tests are documented in [Steering Technical Gate](../../docs/Steering-Technical-Gate-2026-11-10.md). Do not conceal this as a guaranteed run-isolation property; investigate an upstream fix before production release.

## Non-Goals

Steering does not add attachments, target individual workflow participants/background agents, restart a stopped run, edit instructions already submitted, or replace existing approval, cancellation, transcript or compaction mechanisms.

## Acceptance Criteria

- Steer is available during supported active direct Saved Agent run and is absent when no active run or a workflow is running.
- Sending Steering does not cancel an ongoing generation/tool call or start a parallel Harness run.
- Ctrl+Enter uses Steer in supported active mode and ordinary Send when idle; file attachments are preserved and prevent Steering.
- Each instruction retains identity/order/status and successful submit alone does not claim delivery.
- Native late-Steering may cause a second model request within the *same* run; it counts toward ordinary usage/trace.
- A failed admission leaves composer text intact and creates no transcript entry.
- Pending approval, cancellation, reset and completion close new admissions; previously accepted unacknowledged instructions become Not delivered.
- Transcript text/Markdown/HTML export and Saved Chats preserve the individual status and run identity.
- UI limitation regarding possible stale native queue is documented and tested separately.

## Verification

Deterministic Harness fake-client integration covers the native late continuation and the known stale-queue behavior. Root-model observer tests verify distinct IDs and that streaming delivery cannot be acknowledged before model enumeration. UI manual tests cover active direct-agent Steer, Stop, Ctrl+Enter, attachments, approval pauses, navigation and Saved Chat restore.
