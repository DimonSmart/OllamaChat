# IDD-0004.spec-vector-search

## Intent

Enable retrieval over independently managed knowledge stores and show their document, indexing, and search state.

## Related Specifications

Related: IDD-0001, IDD-0005, IDD-0010.

## Behavior

Users manage named Knowledge Stores independently from agents. A store owns its documents, embedding and chunking configuration, and persisted vector index. An agent can attach multiple stores and a store can be shared by multiple agents without copying documents or vectors. Users can inspect and edit a store's name, description, configuration, documents, and index state, and search returns ranked content segments with store, file, and available section identity.

The Knowledge Stores page presents stores in a compact master/detail workspace. The store list supports case-insensitive local filtering by name and clearly identifies the selected store and its index state. The selected store editor groups general details, index configuration, and documents; save and reindex are primary actions while store deletion remains available as a destructive action without competing with them. The document toolbar supports multiple-file upload, shows the selected store's document count, aggregate source size, and index state, and provides case-insensitive local filename filtering. Filtered documents are displayed in a compact client-side paged list with 25, 50, and 100-row page sizes. File sizes and update timestamps are readable at a glance, and document states are visually distinct from ordinary text.

Knowledge Store documents retain both the original uploaded source and a canonical Markdown representation. Markdown and plain-text files are normalized directly; complex supported formats are converted to Markdown through the application-managed MarkItDown boundary. Canonical Markdown is the single internal representation between conversion and indexing: it is normalized only for line endings, emptiness, and stable trailing whitespace, then chunked directly as Markdown text with heading awareness before embedding. Reindexing for chunking or ingestion-format changes reuses the saved canonical Markdown without reconverting the original source.

A document-upload batch is bound to the Knowledge Store selected when the batch begins. Its transfer progress is shown only while that store is displayed; changing the displayed store does not move that progress or the batch destination to another store. Returning to the batch's store shows its current progress. When processing completes, the page refreshes without replacing the user's current store selection, the file-selection control is cleared, and the uploaded documents are represented by that store's document list. A failure to ingest one file reports that file's error and does not prevent the remaining files in the batch from being processed; progress counts every completed attempt.

The Knowledge Store document list lets users open a document's retained original source without exposing server filesystem paths. During indexing, the list identifies the active document and shows its current chunk-based progress; documents already completed in the run are indexed and documents awaiting their turn are pending. This progress is runtime telemetry only and is not persisted as Knowledge Store state.

Knowledge Stores are created and managed independently from agents. Documents are uploaded directly to the selected Knowledge Store; the application does not automatically import files from legacy agent-owned storage. Users who still have legacy files must create a new Knowledge Store and upload the original documents again. The current indexer builds vectors only from each document's persisted canonical Markdown.

When indexed attached knowledge exists, chat retrieval is enabled automatically. Agents that support function calling can search their attached knowledge on demand with focused queries and may search more than once in a run. Agents without function calling receive retrieval before an invocation, using a short recent conversation context. An agent without ready attached knowledge has no knowledge-search capability.

## Durable Architecture And Constraints

Retrieval is scoped exclusively to the Knowledge Stores attached to the selected
agent. A multi-store search obtains results from those stores, ranks them
globally, and applies the result limit once. Search returns only content whose
relevance meets the configured retrieval threshold; a query with no sufficiently
relevant attached content returns no results. This is a normal outcome and does
not add unrelated knowledge to chat context.

Indexing is an explicit background operation. Each store reports NotIndexed,
Indexing, Ready, Outdated, or Failed. Ready means the persisted index was built
with exactly the current embedding provider identity, model, dimension,
chunking settings, and ingestion/index format. Changing any of those settings
makes the store Outdated and rebuilds that store without affecting other stores.
Changing a document reindexes only that document; a document becomes current in the index only after its indexed source version matches its current source version. Changing embedding identity, dimension, chunking settings, or ingestion format makes the entire store Outdated and rebuilds that store without affecting other stores. Search is read-only: it must
never create, delete, replace, invalidate, or rebuild a persisted index. A query
whose embedding is incompatible with a ready index fails safely and reports that
reindexing is required.

Deleting a document removes only that document's vectors. Deleting an agent leaves its stores intact. Deleting a store removes its agent bindings, stored source and canonical content, metadata, and only that store's vectors.

Retrieved file content is untrusted reference data, not agent instructions. The runtime keeps retrieval separate from the agent's instructions and does not expose a way for a model to select another agent's knowledge source.

## Non-Goals

This surface does not manage general-purpose document libraries.

## Acceptance Criteria

- Search results identify their source file and relevance score.
- An unrelated query returns no knowledge results once the configured relevance
  threshold is not met.
- Indexing state remains visible while processing is in progress.
- Chat retrieval does not use stores not attached to the current agent.
- A Knowledge Store can be shared by multiple agents and an agent can attach multiple stores.
- Search never mutates the vector index, including when embedding dimensions differ.
- Changing a store's indexing configuration makes it Outdated until rebuilt.
- Updating one document does not regenerate embeddings for other documents in the store; changing indexing or ingestion configuration rebuilds the whole store.
- Uploaded source and canonical Markdown persist separately; direct Markdown chunking preserves available heading context in retrieved chunks, including valid Markdown task lists and fenced code blocks.
- Changing the displayed store during a document-upload batch does not place any file from that batch in the newly selected store, and the page remains on the user's latest selection after the batch refreshes.
- A document-upload batch's progress is visible only for its destination store; switching stores clears the displayed file selection and does not imply that another store is uploading.
- After a document-upload batch completes, its progress and selected filenames are no longer displayed, and successfully uploaded documents appear in the destination store's document list.
- A user can open a retained original document source from the Knowledge Store document list without receiving a server filesystem path.
- During indexing, the document currently being processed displays chunk-based progress, while completed and queued documents are distinguished as Indexed and Pending; this transient progress is not persisted.
- Knowledge Store and document searches filter only the already loaded items for the current page and do not call a backend search API.
- Document pagination is applied after the selected store's local filename filter and offers 25, 50, and 100 rows per page.
- Complex document conversion is delegated to the application-managed MarkItDown infrastructure rather than application-specific Office or PDF parsing or user-configured MCP servers.
- Deleting an agent leaves shared stores intact; deleting a store removes its bindings and only its data.
- Legacy agent-owned RAG files are not automatically imported or used by Knowledge Store retrieval or indexing.
- Function-capable agents do not retrieve solely because a user message was sent; they can invoke knowledge search when it is relevant.
- Agents without function calling continue to receive relevant attached knowledge during chat.
- Retrieved knowledge is treated as untrusted reference data rather than instructions.

## Verification

Automated coverage verifies many-to-many bindings, shared-store retrieval,
global result limiting across multiple stores, document-only reindexing,
configuration invalidation and full rebuild, direct Markdown ingestion including
task lists, heading context and bounded oversized blocks, safe dimension-mismatch
search, independent agent/store deletion, retained-source reopening, and runtime
document indexing progress lifecycle, and upload-batch store binding and
store-scoped progress despite selection changes during processing. Manual
verification confirms that an individual upload failure does not stop the
remaining files in its batch, and that completing a batch clears the displayed
file selection while its successful documents appear in the destination store.
Manual verification confirms Knowledge Store management, attachment selection in
the agent editor, and that a function-capable agent can answer a unique fact
from an attached store after an on-demand knowledge search without searching for
a greeting.
Manual verification also covers the compact master/detail Knowledge Stores
workspace in light and dark themes, including local store and document filtering,
document pagination, store-scoped upload progress, source reopening, and
indexing progress.
