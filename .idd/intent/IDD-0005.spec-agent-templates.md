# IDD-0005.spec-agent-templates

## Intent

Let users manage reusable agent definitions that combine instructions, optional model settings, tool access, and connected Knowledge Stores.

## Related Specifications

Related: IDD-0001, IDD-0004, IDD-0006, IDD-0007, IDD-0021, IDD-0022, IDD-0024, IDD-0025, IDD-0026.

## Behavior

Users create, search, edit, delete, and restore templates. A template can define identity, summary, instructions, optional model tuning, tool selection, MCP-server bindings, connected Knowledge Stores, an explicit shell-execution opt-in, optional Todo Provider, Agent Mode Provider, File Access Provider, compaction, RAG Provider profiles, and zero or more saved Background Agents. Background Agent selections retain saved-agent identities rather than copies of their configuration. The editor provides a compact search control for adding eligible Background Agents by name or summary, shows their name and summary in search results, and represents selected agents as removable chips. It supports selecting multiple agents, excludes the template currently being edited, and does not offer an already selected agent again. A template selects File Access policy only; it never stores a user workspace directory or sandbox profile. The RAG Provider selection is optional and offers Built-in defaults rather than a disabling selection; connected Knowledge Stores remain the independent signal that retrieval is available. The editor connects or disconnects existing stores; it does not manage their documents.

When a saved agent is run, each selected provider profile configures that agent's runtime provider for the session. An unselected provider remains unavailable; deleting a selected profile leaves the agent's saved selection intact but that provider is unavailable until the selection is changed. Provider state is preserved by the agent session. A saved agent may opt in to shell execution independently of File Access. Shell opt-in only exposes shell tooling when the launch selects a compatible sandbox profile and session workspace; without the explicit opt-in, a selected sandbox profile does nothing for that agent. A saved agent may also opt in to automatic TODO completion with a positive maximum iteration count. The opt-in is valid only when both provider profiles are selected and the selected mode profile contains the exact runtime mode name `execute`; autonomous continuation is restricted to that mode. In all other cases, a user message runs once and stops.

When a saved agent with Background Agents starts as a direct Harness agent, each selected saved agent is independently resolved with its own saved model, instructions, tools, retrieval, skills, File Access, shell, compaction, and other supported runtime configuration, then made available to the parent through Harness Background Agents. The Harness, rather than an OllamaChat workflow or custom delegation tool, decides whether and how to delegate. A child selected as a Background Agent does not expose its own Background Agents during that parent launch; when launched directly itself, its saved Background Agents are available normally. A configured Background Agent must be a distinct existing saved agent, and duplicate or empty identifiers do not create duplicate runtime agents. Selected Background Agent names must be non-empty and unique without regard to case. A parent with one or more Background Agents requires a model that supports function calling. The parent session owns all child runtime resources for its lifetime and uses the same session workspace, sandbox, and approval semantics. The session-state panel identifies the Background Agents available to the direct parent agent.

Direct Harness saved-agent conversations may be explicitly exported and restored as sensitive session snapshots. OllamaChat records compatibility and launch metadata with the opaque Microsoft Agent Framework session payload, but does not interpret or reconstruct provider state. Restore builds the current saved-agent runtime normally and uses that compatible agent to deserialize the session; it never replays the visible chat transcript or invokes model, tools, retrieval, or Background Agents before the user's next message. A snapshot is accepted only for the same saved agent, model server, model, unchanged saved-agent configuration, and effective MCP bindings, and only when its workspace and sandbox profile remain available. MCP-binding comparison preserves the effective tool surface: binding and server identities, enablement, all-tools selection, selected tools, roots, and parameters must agree regardless of semantically insignificant ordering. A restored conversation begins with fresh session-scoped tool approvals. Export and restore are unavailable for workflows, pending approvals, active runs, and sessions with incomplete Background Agent tasks. Completed task metadata is left to the Framework; continuing a Background Agent task after process restart is not guaranteed.

File Memory is an explicit saved-agent opt-in that defaults to disabled so existing agents retain their behavior. It requires a model with function-calling support; an attempted launch without that capability fails before the agent runs with an error that identifies File Memory. When enabled, it uses the Framework's native Harness capability and an application-managed file store. Memory entries persist only between turns of the same Harness session and remain independent from File Access, workspaces, RAG, Knowledge Stores, skills, and chat history.

## Durable Architecture And Constraints

Template-specific values may defer to application defaults when omitted.

## Non-Goals

This surface does not configure server connections or author workflow source.

## Acceptance Criteria

- Required agent identity and instructions are validated.
- Connected Knowledge Stores expose their readiness state.
- Restoring shipped templates preserves custom templates.
- Each provider selection is optional and offers the available profiles plus no selection.
- The optional compaction-profile selection is retained by template creation, editing, copying, and execution mapping; an unavailable selected profile is not silently replaced with no selection.
- The optional RAG Provider profile selection is retained by template creation, editing, copying, and execution mapping; a missing saved profile reports that selection as unavailable rather than silently using built-in defaults.
- A selected Todo Provider profile exposes todo management to the running agent using its saved configuration.
- A selected Agent Mode Provider profile exposes its saved modes and default mode to the running agent.
- A selected File Access Provider profile enables its saved file-access policy for a direct saved-agent session, whose workspace is selected separately for that conversation.
- The saved-agent editor exposes an explicit File Memory switch that defaults to off, persists with the template, and enables native file-based agent memory for the direct Harness session.
- File Memory survives later turns of its enabled Harness session but does not transfer to another chat session.
- A direct saved agent with File Memory fails before launch when its model does not support function calling.
- The saved-agent editor exposes an explicit shell enablement switch that defaults to off, persists with the template, and does not store any sandbox profile or workspace selection.
- A shell-enabled saved agent requires a launch-time sandbox profile and workspace, and a saved agent without shell enablement never receives shell tools even when a sandbox profile is selected at launch.
- The saved-agent editor exposes the TODO-completion opt-in and maximum autonomous iterations, defaults them to disabled and 10, and prevents saving an enabled configuration without the required profiles, an `execute` mode, and an iteration count from 1 through 100.
- An enabled saved agent continues a user-triggered run only while the current session mode is exactly `execute` and TODOs remain, stopping when TODOs complete, the configured limit is reached, or the run is cancelled. Reaching the limit leaves the session usable and preserves remaining TODOs.
- The saved-agent editor provides case-insensitive Background Agent search by name and summary, shows each result's name and summary, and displays selections as removable chips without permanently listing all agents.
- The saved-agent editor persists multiple Background Agent selections by saved-agent identity, excludes self-selection and already selected agents, and retains the selections when an agent is copied.
- A direct saved agent with Background Agents makes the selected child agents available through the standard Harness capability; each child uses its own saved configuration, and child Background Agent selections are not recursively expanded.
- A direct agent with configured Background Agents fails before launch when its model does not support function calling or a configured child saved agent is missing.
- A direct agent with configured Background Agents fails before launch when a selected child has an empty name or selected child names duplicate one another without regard to case.
- Session state identifies the Background Agents available to a direct saved agent, including their name and summary.
- A direct Harness saved-agent session can be explicitly exported and restored through the Framework session serialization APIs without replaying the chat transcript.
- Restore rejects unsupported snapshot formats, missing or incompatible saved agents/models, changed saved-agent configuration or effective MCP bindings, unavailable workspace or sandbox profile, malformed session payloads, and incomplete Background Agent tasks with a user-facing error while leaving the current conversation usable.
- Restoring a snapshot replaces the direct Harness runtime only after the replacement runtime and session have been created successfully, and the session-state panel reads its state from the restored session.
- Session-scoped approvals and in-flight Background Agent work do not survive export and restore.

## Verification

Automated coverage verifies template validation, model selection, tool bindings, retrieval attachments, provider-profile propagation, shell opt-in propagation, Background Agent selection persistence and validation, one-level Harness Background Agent resolution with independent child configuration, function-calling launch validation for Background Agents and File Memory, child-resource cleanup, Framework session serialization round trips and compatibility rejection, atomic restore failure, and the enabled/disabled TODO-completion invariants. Restore coverage proves that no model, tool, or retrieval call occurs before the next user message. Manual verification confirms that Background Agent search filters by name and summary, selected agents become removable chips and cannot be selected again or selected as the edited template, a selected profile retains todo or mode state within a chat session, shell enablement only takes effect when launch selects a sandbox and workspace, plan mode does not continue automatically, execute mode completes TODOs up to the configured limit while the session-state panel refreshes after the run, a parent agent can delegate eligible work to its configured Harness Background Agents, and an explicitly restored Harness snapshot retains conversational context without rebuilding it from chat bubbles.

P1 Background Agents are functionally ready. Lifecycle cleanup is temporarily blocked by upstream Microsoft Agent Framework API [microsoft/agent-framework #7602](https://github.com/microsoft/agent-framework/issues/7602): the published NuGet API does not yet provide `BackgroundAgentsProvider.ReleaseSessionAsync`. Once the first .NET NuGet release containing that API is available, OllamaChat must update MAF and add cleanup and lifecycle tests. Until then, detached Background Agent tasks cannot be guaranteed to be cancelled or released.
