# IDD-0023.spec-compact-user-interface

## Intent

Provide a compact, desktop-oriented interface that presents administrative controls and dialogs efficiently without sacrificing readability or accessibility.

## Related Specifications

Related: IDD-0001, IDD-0003, IDD-0005, IDD-0006, IDD-0007, IDD-0010, IDD-0021, IDD-0022.

## Behavior

Administrative pages, forms, tables, and dialogs use a consistent compact visual density. Related controls are closely grouped, while distinct logical sections remain visually separated. Common actions and tables use compact controls. Long-form prompt, configuration, and source editors retain sufficient usable space for authoring their content. Compact conversation-level state is disclosed in-place rather than as a persistent side panel or separate page. Reusable server-and-model selection controls provide a dense form presentation and a compact presentation. The compact presentation summarizes the current server and model in one short, secondary-action line and reveals the server and model fields in a keyboard-accessible popover on demand. It remains usable on narrow viewports, truncates long summary text without shrinking the interactive target below a usable size, and exposes the complete selection through accessible content.

On the primary chat routes, server-and-model selection is colocated with the message-composition workflow rather than the upper application toolbar. Before a session starts, the compact selector appears in the launch area so the launch can be configured and validated. After the session starts, the same selection state is controlled from inside the message composer. The chat page exposes only one interactive selector for its primary model at a time. The composer selector opens toward available viewport space and remains present but disabled while generation or another existing composer-blocking state forbids selection changes, avoiding layout movement. Other pages that depend on global model selection retain a compact selector in the upper toolbar.

The default layout is content plus spacing. Containers, surfaces, borders, elevation, icons, chips, colors, headings, captions, helper text, and other visual elements are introduced only when they communicate information or structure that is not already apparent from the surrounding content. Whitespace and typography are preferred to decorative cards and dividers. A field or small field group is not given its own surface merely for emphasis. Explanatory text does not repeat a title, label, placeholder, value, or visible action. Technical or rarely used information is disclosed when needed instead of permanently occupying the primary layout. Icons, chips, and color are not decorative accents.

Elements with the same purpose use the same visual pattern throughout the application. Existing shared patterns take precedence over local preferences. A new page reuses the applicable page, toolbar, form, table, status, and dialog patterns unless a functional difference requires an exception; a durable exception is recorded by the owning feature specification. Visual distinction represents a difference in semantics, state, or behavior, not an individual screen preference.

Shared application UI components are the canonical implementation of recurring application visual patterns. When an equivalent shared pattern exists, pages reuse it instead of recreating the underlying MudBlazor composition locally. Equivalent page layouts, page headers, management toolbars, sections, CRUD actions, search placement, tables, empty states, dialogs, and form actions do not have page-specific implementations without a functional reason. A new visual pattern requires a functional, semantic, accessibility, or responsive-layout reason; page-specific visual preference is insufficient. Shared components hide stable application conventions, not arbitrary fragments of component markup, and are extracted only after repetition is demonstrated.

Content uses only the hierarchy needed to understand and operate the page: page title, independently meaningful section title, field or control label, and necessary secondary or help text. Labels, placeholders, helper text, descriptions, and tooltips do not repeat the same meaning. Placeholders are used for search, input examples, or where a visible label is genuinely unnecessary; they do not replace an accessible name. Detailed troubleshooting and rarely needed technical information do not permanently occupy the main layout.

Each local action group normally has one primary action. Ordinary action buttons and dialog actions use the compact supported control size. Primary actions use a filled primary presentation; secondary actions use default-color outlined or text presentation; destructive actions use error semantics. Table row actions use compact icon controls. Icon-only controls have accessible names and, where their meaning is not otherwise evident, tooltips. Larger action controls are reserved for a distinct interaction role such as a touch-oriented or specialized control. Primary and selected or active state use the primary color. Success, warning, and error colors communicate their corresponding state only; the secondary theme color is not a generic secondary-action semantic. A local visual group normally has one main color accent. Status information is calm and compact, with color used only for meaningful state and never as the sole state indicator. Compact metric summaries may use concise hover tooltips to disclose the meaning of otherwise space-efficient symbols or abbreviated values.

Management pages use a shared geometry for content start, title, toolbar, search, and table or list spacing. Their CRUD toolbar places the primary action and any lower-weight actions before a responsive spacer and search. Management tables use compact density, restrained row actions, accessible icon controls, and consistent empty and pagination presentation. Utility forms and specialized chat or editor views use the shared form pattern without being forced into management-page geometry. Forms use a consistent default field density, responsive grid grouping, concise help text, and primary-then-secondary action ordering. MudBlazor component and layout APIs are preferred before utility classes, shared semantic application CSS, and finally scoped feature CSS.

Management tables show identifying and decision-relevant information rather than every persisted property of the underlying model. Secondary and rarely used configuration remains available through editing or details. Empty states use a short neutral message; they do not repeat an adjacent create action or add a large decorative icon. Row actions that have equivalent semantics use the same icon, ordering, sizing, color semantics, accessible name, and tooltip behavior.

Application settings are organized as a compact settings form with independently meaningful sections, not a collection of decorative cards. Section headings and spacing establish hierarchy. Settings retain explanatory text only where a user cannot reasonably infer consequences or semantics from the label and control. Complex repeated entities, editor stages, and independently actionable items may use restrained outlined grouping or expansion panels when that grouping materially aids operation.

Form field width reflects the expected content rather than automatically filling the available container. Names of primary entities, URLs, paths, commands, descriptions, prompts, configuration text, and multiline editors may use the full form width. Bounded numeric inputs, enum selectors, switches, and other short-value controls are grouped into responsive rows and do not consume the full desktop width without a functional reason.

The upper application toolbar remains a single usable row at every viewport width. At narrow widths it hides the long application title before allowing toolbar controls to overflow. Where the toolbar provides server-and-model selection, it uses the compact summary-and-popover presentation at every viewport width; selection remains available by mouse and keyboard and model names remain readable rather than being reduced below usable target sizes.

MCP bindings use one shared selection pattern wherever a chat launch or saved-agent template configures them. The primary presentation is one compact secondary-action summary, showing `MCP · None`, the single bound server's display name, or the number of bound servers. Its keyboard-accessible popover lists each binding by one visible name and one explicit state: `All tools`, a selected-tool count including `No tools`, `Off`, or a compact warning when binding-specific tool discovery fails. Display names take precedence over registry names in this summary. Binding enablement, individual tool selection, Roots, per-usage overrides, ordering when relevant, and other advanced settings remain available only after the user opens that binding's details; the primary presentation does not repeat the same state through headings, labels, switches, captions, and helper text.

Adding an MCP binding first asks the user to choose a registered server and does not mutate the configuration if selection is cancelled. Choosing a server creates the binding enabled, exposing all tools, with no selected-tool entries, so the common path requires no further configuration. A user-visible binding always identifies a concrete registered server; enablement applies only to an identified binding. A disabled binding retains its detailed configuration and remains visible as `Off`. The empty popover distinguishes no bindings from no registered servers, and the latter provides access to MCP server management without creating a placeholder binding. Loading and binding-specific failures stay compact and do not replace the surrounding layout with a large status surface.

## Durable Architecture And Constraints

The application has one shared visual theme and one theme provider. Shared typography, layout dimensions, dialog spacing, surface spacing, and semantic application CSS patterns are defined centrally. The implementation remains MudBlazor-first: it uses the MudBlazor component and layout API before shared application components, shared semantic CSS, and feature-specific scoped CSS, in that order. It does not build a parallel control library or wrap ordinary fields and buttons without a proven application-level convention. Component density uses supported MudBlazor mechanisms and does not depend on removed or unsupported global component-default APIs. Static authored CSS is not embedded in application Razor markup; necessary shared or feature-specific presentation rules have semantic classes. Dynamically computed styles remain permissible when no component API or semantic class can reasonably express the result. Administrative forms use MudGrid breakpoints for responsive field grouping. Ordinary form-field widths are not controlled by arbitrary fixed pixel values. Compact fields use the full row on narrow viewports and share rows on wider viewports. Dynamic or externally defined fields may remain full-width when their expected content length is unknown. The compact presentation preserves keyboard navigation, focus visibility, readable text, usable interactive targets, and responsive layouts.

## Non-Goals

This specification does not alter configuration, validation, CRUD, workflow, active-session model resolution, chat, attachment, voice-input, send/stop, or dialog semantics. It does not introduce reasoning-effort selection or require reducing dialog widths or multiline editor sizes solely to make the interface denser.

## Acceptance Criteria

- Administrative pages and dialogs visibly present more useful information within a typical desktop viewport while remaining readable.
- Ordinary form controls, action buttons, and administrative tables use compact density where supported.
- Server-and-model selection retains dense ordinary fields in forms, while toolbar and composer contexts use one compact summary control with server and model fields disclosed in a popover and no clear-selection action.
- Primary chat routes do not show server-and-model selection in the upper toolbar, show exactly one interactive primary-model selector in the launch area before session start, and move that selector inside the composer after session start.
- The chat selector updates the shared UI model selection and preserves existing model persistence and launch-validation behavior without changing active-session model resolution.
- The composer selector opens into usable viewport space and remains visible but disabled during generation or an equivalent composer-blocking state, without changing composer layout.
- Dialogs and cards have reduced shared internal spacing without overlapping validation or helper text.
- Prompt, configuration, and source editors remain practical to read and edit.
- Bounded numeric inputs and short enum controls do not appear unjustifiably stretched on desktop, and related short controls share responsive rows.
- Form groups collapse to a single column on narrow viewports without horizontal scrolling; helper text and validation remain visible, and tab navigation follows visual field order.
- The application continues to provide accessible keyboard interaction, visible focus, meaningful accessible names and disabled state, Escape dismissal for popovers, and responsive layouts without horizontal scrolling at narrow viewport widths.
- Management pages share title, toolbar, search, and table or list geometry; CRUD toolbars align their primary action and search without page-specific offsets.
- Management pages use the canonical shared page and CRUD-toolbar patterns, while independently meaningful settings and editor sections use a shared non-elevated section pattern.
- Management tables expose identifying and decision-relevant columns; full persisted configuration remains reachable without crowding the list view.
- Equivalent actions, fields, tables, row actions, dialogs, and status information follow their shared compact patterns, with accessible names for icon-only controls.
- The interface avoids duplicated explanatory text and does not use color as the only indication of capability or status.
- Chat launch and saved-agent template editing use the same compact MCP binding selector, with one summary control and a disclosure popover rather than a permanently expanded editor.
- The MCP summary and rows expose server identity and `All tools`, selected-tool count, `No tools`, `Off`, or warning state without displaying advanced configuration on the primary level.
- Adding an MCP server changes bindings only after a concrete registered server is selected and initializes it as enabled with all tools exposed; cancelling selection leaves bindings unchanged, and no active binding can lack server identity.
- Disabled MCP bindings retain their configuration, and existing Roots, overrides, and selected-tool configuration remain reachable through binding details.
- Application settings use section hierarchy and spacing instead of a decorative card for each setting group.
- Empty states are concise and neutral, without decorative icons or instructions that repeat a visible action.
- Decorative surfaces, borders, elevation, icons, chips, color accents, captions, and helper text can be removed without loss of information wherever surrounding content already communicates the same structure or meaning.
- Static authored CSS rules are absent from application Razor markup except for dynamically computed presentation that cannot be represented otherwise.

## Verification

Manual MCP-selection verification covers no bindings, no registered servers, one and multiple bindings, all-tools and zero/one/multiple selected-tool states, disabled and mixed states, binding-specific tool-load failure, cancelled server addition, saved-template reopen, chat launch validation after edits, preserved Roots and overrides, light and dark themes, narrow layouts without horizontal scrolling, visible focus, keyboard navigation, and Escape dismissal.

Manual verification covers light and dark themes; administrative CRUD pages; forms with validation and multiline editors; dialogs with several grouped controls; dense tables; and narrow viewport layouts, including responsive form groups that retain full-width long-form editors while stacking compact controls into one column. It compares management and provider/profile pages for shared content start, title, vertical rhythm, primary-action geometry, optional search geometry, toolbar-to-table spacing, table density, empty states, row actions, and dialog action hierarchy. It verifies Application Settings, Models, Knowledge Stores, Vector Search, MCP Playground, and dialogs; checks that removable decoration and duplicated explanation are absent; and confirms that icon-only controls have accessible names and capability or status state is not color-only. It also covers compact global selection outside chat, selection in the chat launch area, its transfer into the running-session composer, upward composer popover placement, server-driven model reload, persistence and launch validation, disabled generation state without layout movement, long names and keyboard interaction at narrow widths, and preservation of the ordinary form presentation. Existing behavioral verification continues to establish that active-session model resolution, configuration, validation, attachments, voice input, send/stop behavior, workflows, and dialogs retain their semantics.
