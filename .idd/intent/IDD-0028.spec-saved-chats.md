# IDD-0028.spec-saved-chats

## Intent

Provide locally persistent, resumable saved chats for direct agents and workflows.

## Related Specifications

Related: IDD-0001, IDD-0010, IDD-0023.

## Behavior

Completed stable turns are saved automatically by default. A saved chat has a user-editable title, metadata for listing and search, its complete transcript, launch information, and, for direct saved agents, a native runtime-session snapshot with compatibility metadata. The first user request supplies a deterministic title of at most 32 Unicode characters; a manually renamed title is retained. Users can search, rename, open, and delete saved chats on a dedicated Chats page. The selected chat has a compact destructive delete control alongside its other actions. Deletion removes that saved chat from local storage and the list; it does not reset or otherwise alter the current active conversation. Opening a saved chat gives immediate, compact in-row feedback and prevents concurrent or conflicting Chats-page operations until the attempt finishes. A long-running restore discloses meaningful real restoration phases when available, without implying an artificial percentage. Opening validates the saved format and target, including the current definition, launch requirements, and native-session compatibility, before replacing a stable current chat; active, approval-paused, failed, or otherwise unstable chats are not silently replaced. An unsuccessful restore leaves the current chat unchanged, clears the opening state, and reports a clear error. A direct saved agent restores its compatible native session and transcript, so the next turn continues the previous Harness context. A workflow has no native session and resumes using its current resolvable definition and restored transcript as conversation history. Restoring either kind retains its resolved presentation participant and attribution.

The active saved chat retains the storage root from which it was opened. Changing the Saved Chats root affects the Chats list and newly created saved chats, but neither moves nor duplicates an open chat. Persistence failures do not fail a completed response; while automatic saving is enabled, the user receives one compact warning when persistence first becomes unhealthy and is notified again only after a later successful checkpoint restores health.

## Durable Architecture And Constraints

Each chat is an independently written versioned JSON document under the configured local Saved Chats root. Persisted JSON, including nested launch and native-session metadata, uses one consistent naming policy. Checkpoints replace the complete document atomically with a unique same-directory temporary file and per-document synchronization; concurrent saves and a rename do not corrupt JSON or discard a manual title. The prior valid document remains available if replacement fails. The list reads only summary metadata, ignores temporary files, and tolerates corrupt individual files. A newer unsupported format is rejected without attempting an unknown deserialization. Existing chats remain openable when automatic saving is disabled.

A checkpoint is created only after a successful completed turn in the current runtime generation, with no streaming message, pending approval, reset requirement, or incomplete native background work. Direct saved-agent checkpoints serialize the completed Harness AgentSession together with the saved-agent id, definition revision, model, launch overrides, and snapshot format; they do not persist approval grants, pending approvals, traces, cancellation or other runtime-transient state, or UI state. Native Harness session serialization is an internal implementation detail of resumable Saved Chats and has no separate user-facing import/export workflow.

## Non-Goals

Saved chats do not provide folders, tags, pinning, cloud synchronization, encryption, full-text transcript indexing, autosave timers, LLM title generation, or a separate manual Harness-session import/export workflow.

## Acceptance Criteria

- A completed chat persists across navigation, circuit shutdown, and application restart.
- Continuing a saved chat updates its existing document; New Chat does not delete it.
- The selected saved chat can be deleted from the Chats page; deletion removes only its saved document and does not alter the active conversation.
- Search is local and list ordering is most recently updated first.
- Restored messages retain their visible content and metadata, and a direct agent continues its native context when compatible.
- Opening an invalid or incompatible saved chat leaves the previous usable chat intact.
- Opening a saved chat gives immediate in-row activity feedback, exposes real restore phases when available without artificial progress, and prevents duplicate or conflicting Chats-page operations until completion.
- A direct saved-agent checkpoint contains a native session; a workflow checkpoint does not.
- Concurrent checkpoint and rename activity retains valid JSON and the manually assigned title.
- Continuing a chat opened from an earlier root continues to update that root after settings select a new root.
- Saved Chats settings include automatic-saving, root, and reserved server, model, and prompt values for future title generation; the current title generator remains deterministic.
- Failed, cancelled, streaming, or approval-paused turns cannot overwrite the last stable checkpoint.
- The Chats page follows the shared compact UI patterns.

## Verification

Automated coverage verifies atomic replacement and concurrent save/rename safety, resilient summary listing and JSON naming round trips, deterministic title normalization, settings defaults and backward-compatible loading, stable-turn checkpoint rules, transcript restoration through chat events, direct-agent native-session resume compatibility and workflow history after reopen. It verifies rejected restores for missing or invalid launch dependencies and incompatible native sessions leave the active chat usable, restoration phase notifications describe actual preparation steps without a successful state after failure, participant restoration uses the current resolved definition, root changes do not relocate an open chat, and deleting a saved chat removes only its persisted document. Manual coverage verifies search, rename, deletion of the selected chat, compact persistence errors, title-generation setting presentation, immediate in-row opening feedback and phase changes, prevention of duplicate opens, open errors that clear the busy state, navigation placement, and reopening after restart.
