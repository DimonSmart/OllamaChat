# IDD-0001.spec-agentic-chat

## Intent

Provide an interactive chat surface for running a selected agent or saved workflow.

## Related Specifications

Related: IDD-0002, IDD-0004, IDD-0005, IDD-0007, IDD-0009, IDD-0010, IDD-0024, IDD-0025.

## Behavior

Users select an available agent or workflow, supply required inputs, and exchange messages. Responses stream into the transcript; users can cancel an active response and copy the conversation as text, Markdown, or HTML. The transcript exposes assistant reasoning and tool activity when supplied by the runtime. Internal runtime feedback used solely to continue an autonomous run is not shown in the user transcript. Direct saved Harness-agent conversations surface a pending tool-approval request with the requested tool name and arguments. The user may approve that call once, deny it, approve that tool for the current chat, or approve that exact call for the current chat; the decision continues the same agent session. Approval protocol messages are controls rather than transcript messages, and an approval-only response does not create an empty assistant message. While an approval is pending, ordinary chat input and unrelated direct-session mutations, including mode switching, are unavailable until the approval is resolved or the conversation is reset; a pending approval is not an active response. A direct-agent conversation with available runtime session state exposes an initially closed Session state control beside the conversation copy action. It opens a local right-side overlay panel over the transcript without changing the message area or message-input dimensions; the panel can be closed from either control and closes when session state is unavailable. The panel shows the current runtime mode, TODO list, workspace binding, and sandbox state when those capabilities are available, including an empty TODO list; it refreshes after session creation, each successful runtime tool action that changes the session mode or TODO list, completed runs, runtime mode changes, sandbox lifecycle changes, workspace changes that are allowed for the current session kind, and conversation reset. When the direct session has an Agent Mode Provider, its effective runtime modes are offered as a compact selector. The user may select a mode before the first message or between runs; the selection changes only the current session's runtime mode, does not add a transcript message or run the agent, and applies to the next invocation. The selector is unavailable during an active run or pending approval and absent when no Agent Mode Provider exists; a single effective mode is displayed read-only. Workflow conversations do not present an ambiguous combined session state.

The Session state panel displays one shared workspace binding at most once, presents the File Access profile name separately when one is available, and limits sandbox details to the sandbox profile, image, and state.

## Durable Architecture And Constraints

Conversation execution supports both direct agents and workflow-based agents.

Session-state display is a projection and control surface for the active direct conversation's runtime session. Agent-session state remains the sole owner of modes, TODOs, session-scoped tool-approval rules, and any sandbox instance; saved-agent configuration, transcript/tool history, and UI state do not substitute for it. A pending approval pauses autonomous work without destroying that session, and reset or new chat invalidates the pending approval and its session-scoped approvals. Intermediate refreshes observe the active session and must not restore state from a cancelled or reset conversation. A saved Agent Mode Provider profile's default initializes each new session only; changing a session mode never changes the saved profile or a different session. The selector uses the effective modes materialized for that runtime agent, so edits to a saved profile do not alter an existing conversation's options. Switching modes preserves the same agent session and its TODO state. When a session runs with a sandbox, the selected sandbox profile, normalized workspace, and sandbox instance are session-scoped launch resources rather than saved-agent configuration.

## Non-Goals

This surface does not define how agents, workflows, servers, or tools are authored.

## Acceptance Criteria

- A valid selection can receive a user message and return streamed output.
- Cancellation leaves the conversation in a usable state.
- Users can export the displayed transcript in each offered format.
- A direct conversation with a mode or TODO capability can reveal its current session state in a right-side overlay without opening a separate TODO page or resizing the transcript or message-input area.
- A direct conversation with an Agent Mode Provider offers its effective runtime modes and confirms the runtime value after a successful change; mode selection is available before the first message and between runs without creating a message, invocation, or new session.
- Mode selection preserves the current session's TODOs and does not modify the saved provider profile; a new chat again initializes its mode from the profile default.
- A direct conversation with a TODO capability distinguishes an empty list from an unavailable capability, and a new conversation does not display TODOs from the previous session.
- Session state displays a shared workspace at most once, separately displays the File Access profile when present, and displays sandbox details without another workspace path.
- During an autonomous direct-agent run, the Session state panel visibly reflects successful TODO and mode changes before the whole run completes, while runtime continuation feedback is absent from the transcript.
- A direct saved Harness-agent conversation shows a pending approval with the tool name and arguments before an approval-required tool runs; approving once, denying, or creating either session-scoped standing approval continues the same session without adding a user transcript message.
- Pending approval disables ordinary input and mode selection without presenting an active-response stop control; it does not set a reset-required state, and reset or new chat makes the old approval impossible to answer.
- Approval-only runtime output produces no empty assistant bubble. A tool call that is subsequently allowed is displayed through the ordinary tool-activity transcript mechanism.
- A workflow conversation does not select or aggregate a participant's session state.
- A direct saved agent that uses File Access or shell execution cannot start without an existing workspace directory; direct agents that use neither capability require none.
- A direct saved agent with shell execution cannot start without a selected sandbox profile whose provider is available; workflow launch applies the same requirement when any reachable participant can execute shell commands.
- Between runs, a user can change the workspace and the same session retains its mode and TODO state only when the session does not have an active sandbox; the control is unavailable during a run or pending approval and becomes read-only for sandbox-backed sessions.
- File-access calls use the existing approval flow, and a file-access call never offers a standing approval.
- Shell calls use the existing approval flow, keep a single sandbox instance for the owning root session, and never execute on the host operating system.

## Verification

Automated coverage verifies streaming, cancellation, transcript state, export formatting, runtime session-state projection, autonomous-run state-change projection, direct-session mode switching without an invocation or session replacement, workspace switching when no sandbox is active, sandbox-backed read-only workspace projection, and tool-approval request projection and continuation. Behavioural approval coverage verifies pause-before-execution, approve-once, deny, session-scoped standing approvals where supported, exact-arguments approval, reset invalidation, and same-session continuation. File-access coverage verifies workspace validation, sandboxing, read-only tool exposure, and rejection of workspace changes during runs or pending approval. Shell coverage verifies launch validation, sandbox state projection, host-independent execution, per-session sandbox ownership, reset cleanup, and rejection of sandbox-backed workspace changes. Manual verification confirms that the session-state overlay preserves independent transcript and panel scrolling, input dimensions, state updates across runs and resets, and mode or eligible workspace changes before the first message and between turns.
