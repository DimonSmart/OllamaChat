# IDD-0001.spec-agentic-chat

## Intent

Provide an interactive chat surface for running a selected agent or saved workflow.

## Related Specifications

Related: IDD-0002, IDD-0004, IDD-0005, IDD-0007, IDD-0009, IDD-0010, IDD-0024, IDD-0025.

## Behavior

Users select an available agent or workflow, supply required inputs, and exchange messages. Responses stream into the transcript; users can cancel an active response and copy the conversation as text, Markdown, or HTML. An active chat session persists for the current Blazor circuit when the user navigates to another application page: its transcript, runtime, pending approval, workspace, sandbox, and session state remain available when the Chat page is opened again. Navigation only detaches the temporary view, and a returning view synchronizes from the existing session before rendering; it does not start another session or replace the active selection with a default. If the saved definition is no longer present in the catalog, the existing session remains accessible under a neutral active-session identity. A user creates a new chat only through the explicit New Chat action, which cancels an active run when necessary and resets the current session; stopping a run alone retains its transcript. Circuit shutdown releases active runtime resources. The transcript exposes assistant reasoning and tool activity when supplied by the runtime. Internal runtime feedback used solely to continue an autonomous run is not shown in the user transcript. A pending tool approval appears in a modal dialog above the current page, independent of transcript scroll position, and requires an explicit decision. It identifies the tool or its category, technical name, arguments, and applicable workspace. The dialog offers deny, approval for the current call, and—when applicable—approval for the current chat session; it cannot be dismissed by backdrop, Escape, or a close control. Each pending request opens at most one dialog, and the dialog closes when its request is answered, cancelled, reset, or no longer pending. Approval protocol messages are controls rather than transcript messages, and an approval-only response does not create an empty assistant message. A session approval always allows the current call and then applies only within that chat session: shell approval covers subsequent sandbox shell commands, File Access approval covers all File Access operations in the same normalized workspace, and another tool approval covers only the same registered tool. Session approvals are cleared by reset or a new chat and are never persisted. While an approval is pending, ordinary chat input and unrelated direct-session mutations, including mode switching, are unavailable until the approval is resolved or the conversation is reset; a pending approval is not an active response. The message composer remains fixed at the bottom of the viewport, centered in the chat area, and has a compact width comparable to a modern conversational interface. Transcript content reserves space beneath its final item so the composer never hides it. The conversation copy control, and the Session state control when runtime state is available for a direct-agent conversation, appear together in the upper application toolbar. Session state opens a fixed right-side drawer from the application viewport without changing the message area or message-input dimensions; the panel can be closed from either control and closes when session state is unavailable. The browser page scrollbar scrolls the complete transcript, while the session-state drawer scrolls only its content vertically when needed. The panel shows the current runtime mode, TODO list, workspace binding, and sandbox state when those capabilities are available, including an empty TODO list; it refreshes after session creation, each successful runtime tool action that changes the session mode or TODO list, completed runs, runtime mode changes, sandbox lifecycle changes, workspace changes that are allowed for the current session kind, and conversation reset. When the direct session has an Agent Mode Provider, its effective runtime modes are offered as a compact selector. The user may select a mode before the first message or between runs; the selection changes only the current session's runtime mode, does not add a transcript message or run the agent, and applies to the next invocation. The selector is unavailable during an active run or pending approval and absent when no Agent Mode Provider exists; a single effective mode is displayed read-only. Workflow conversations do not present an ambiguous combined session state. A completed retrieval is initially represented within its originating assistant message by a compact `(RAG:excerpts:documents)` control; selecting it reveals the retrieval diagnostic and its excerpts.

The right-side inspector dock independently presents Session state and Harness trace panels for direct-agent conversations. Either panel can be opened or closed without changing the other. On wide viewports both panels appear together in one dock; responsive layouts retain their independent availability. Session state continues to display one shared workspace binding at most once, presents the File Access profile name separately when one is available, and limits sandbox details to the sandbox profile, image, and state.

Harness trace captures the real OpenTelemetry activities emitted by a direct Harness agent invocation and retains a bounded, per-chat diagnostic history independently from the serialized agent session. It is available before the first run, updates during a run, and remains available after completion. Each run displays its emitted generic activity hierarchy, timing, status, identifiers, attributes, events, and links, without requiring an external telemetry collector. A span retains at most 100 events; when additional events occur, the inspector shows the first 100 and identifies that the event list was truncated. Trace histories are isolated between Blazor circuits, are cleared by reset, new chat, or restoring a Harness session, and never affect agent execution when capture fails. Sensitive telemetry capture is not enabled; displayed attribute and event values defensively redact secret-bearing keys and bound retained value sizes.

## Durable Architecture And Constraints

Conversation execution supports both direct agents and workflow-based agents. Approval scope, availability, session-grant application, and conversion to framework approval responses are shared by direct and runtime execution paths; the UI does not own approval semantics.

Session-state display is a projection and control surface for the active direct conversation's runtime session. Agent-session state remains the sole owner of modes, TODOs, session-scoped tool-approval rules, and any sandbox instance; saved-agent configuration, transcript/tool history, and UI state do not substitute for it. A pending approval pauses autonomous work without destroying that session, and reset or new chat invalidates the pending approval and its session-scoped approvals. Intermediate refreshes observe the active session and must not restore state from a cancelled or reset conversation. A saved Agent Mode Provider profile's default initializes each new session only; changing a session mode never changes the saved profile or a different session. The selector uses the effective modes materialized for that runtime agent, so edits to a saved profile do not alter an existing conversation's options. Switching modes preserves the same agent session and its TODO state. When a session runs with a sandbox, the selected sandbox profile, normalized workspace, and sandbox instance are session-scoped launch resources rather than saved-agent configuration.

## Non-Goals

This surface does not define how agents, workflows, servers, or tools are authored.

## Acceptance Criteria

- A valid selection can receive a user message and return streamed output.
- An assistant response that performs knowledge retrieval shows a compact, initially collapsed `(RAG:excerpts:documents)` control for its actual attempts, including empty and safe failure outcomes; selecting it reveals the diagnostic, and no diagnostic appears when retrieval was merely available.
- Retrieval diagnostics show the actual query, resolved mode and effective search settings, final model-supplied excerpts, and source metadata as untrusted plain text, and remain attached to only their originating response across streaming, cancellation, and navigation.
- Cancellation leaves the conversation in a usable state.
- Internal navigation preserves the one active circuit-scoped chat session, including streamed messages, pending approval, session-state projection, workspace, and sandbox; returning to Chat restores that session without another launch.
- New Chat is the only user action that resets the session and releases its session-owned resources; stopping an active response does not clear the transcript.
- Users can export the displayed transcript in each offered format.
- The upper application toolbar offers copy formats for the current conversation and, when a direct conversation has a mode or TODO capability, a Session state control that reveals a fixed right-side drawer without opening a separate TODO page or resizing the transcript or message-input area.
- A direct Harness conversation offers an independent Harness trace control in the upper toolbar. Its inspector can be opened with or without Session state, captures actual Harness OpenTelemetry activities even while closed, and shows a bounded per-chat history of live and completed runs without exposing sensitive values or mixing traces from another circuit. Each span shows at most its first 100 events and clearly identifies event-list truncation independently from span-list truncation.
- The page scrollbar scrolls the complete conversation transcript; the drawer does not create a nested transcript scrollbar.
- The message composer remains visible at the bottom of the viewport, and the final transcript item can be fully read without being covered by it.
- A direct conversation with an Agent Mode Provider offers its effective runtime modes and confirms the runtime value after a successful change; mode selection is available before the first message and between runs without creating a message, invocation, or new session.
- Mode selection preserves the current session's TODOs and does not modify the saved provider profile; a new chat again initializes its mode from the profile default.
- A direct conversation with a TODO capability distinguishes an empty list from an unavailable capability, and a new conversation does not display TODOs from the previous session.
- Session state displays a shared workspace at most once, separately displays the File Access profile when present, and displays sandbox details without another workspace path.
- During an autonomous direct-agent run, the Session state panel visibly reflects successful TODO and mode changes before the whole run completes, while runtime continuation feedback is absent from the transcript.
- An approval-required tool call shows exactly one non-dismissible modal request with its category, technical name, arguments, and applicable workspace; approving once, denying, or approving for the current session continues the same session without adding a user transcript message.
- A session approval covers all later sandbox shell commands, all File Access operations in the same normalized workspace, or only the same ordinary registered tool, as applicable; it is cleared by reset, new chat, or an eligible workspace change and is never persisted.
- Pending approval disables ordinary input and mode selection without presenting an active-response stop control; it does not set a reset-required state, and reset or new chat makes the old approval impossible to answer.
- Approval-only runtime output produces no empty assistant bubble. A tool call that is subsequently allowed is displayed through the ordinary tool-activity transcript mechanism.
- A workflow conversation does not select or aggregate a participant's session state.
- A direct saved agent that uses File Access or shell execution cannot start without an existing workspace directory; direct agents that use neither capability require none.
- A direct saved agent with shell execution cannot start without a selected sandbox profile whose provider is available; workflow launch applies the same requirement when any reachable participant can execute shell commands.
- Between runs, a user can change the workspace and the same session retains its mode and TODO state only when the session does not have an active sandbox; the control is unavailable during a run or pending approval and becomes read-only for sandbox-backed sessions.
- File-access calls use the ordinary modal approval flow; session approval covers all File Access operations in the current normalized workspace.
- Shell calls use the ordinary modal approval flow, keep a single sandbox instance for the owning root session, never execute on the host operating system, and can be approved for the current session.

## Verification

Automated Harness trace coverage verifies that a span retains no more than 100 events, reports event-list truncation only when an additional event occurs, and continues to redact and bound retained event-attribute values.

Automated coverage verifies streaming, cancellation, transcript state, export formatting, runtime session-state projection, autonomous-run state-change projection, direct-session mode switching without an invocation or session replacement, workspace switching when no sandbox is active, sandbox-backed read-only workspace projection, and tool-approval request projection and continuation. It verifies Harness trace run correlation and circuit isolation under concurrent activity, generic span-tree construction including roots and orphans, completion status, bounded retention, redaction, reset/disposal cleanup, and independent Session state and Trace inspector states. It also verifies that view disposal does not cancel or reset an active session, and that a replacement Chat view restores its existing state without starting a second session. Behavioural approval coverage verifies pause-before-execution, approve-once, deny, session approval scope, reset invalidation, eligible-workspace-change invalidation, and same-session continuation through both direct and runtime paths. File-access coverage verifies workspace validation, sandboxing, read-only tool exposure, group approval within one workspace, and rejection of workspace changes during runs or pending approval. Shell coverage verifies launch validation, sandbox state projection, host-independent execution, per-session sandbox ownership, session-wide shell approval, reset cleanup, and rejection of sandbox-backed workspace changes. UI coverage verifies one dialog per request, dismissal when pending state disappears, disabled repeated submissions, a compact RAG control that expands to a readable diagnostic in its originating assistant message, and the simultaneous responsive inspector panels. Manual verification confirms that approval dialogs remain visible above a scrolled transcript and that internal navigation during an active or approval-paused conversation preserves the session and that explicit New Chat releases it; it also confirms that the upper toolbar targets the active conversation, the composer remains fixed at the bottom of the viewport, does not cover the final transcript item, the right-side drawer is fixed to the viewport, the page scrollbar scrolls the complete transcript, the drawer scrolls only vertically when its content overflows, input dimensions remain unchanged, and state updates across runs and resets, mode or eligible workspace changes work before the first message and between turns.
