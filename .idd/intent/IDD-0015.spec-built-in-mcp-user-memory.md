# IDD-0015.spec-built-in-mcp-user-memory

## Intent

Expose one explicit, persistent, local string key/value user profile through the existing opt-in built-in MCP server.

## Related Specifications

Related: IDD-0007, IDD-0008, IDD-0010.

## Behavior

The built-in server keeps its original ID, key and displayed name. It exposes exactly three tools:

- profile_get reads a key and returns exists=false when absent.
- profile_get_all reads all current values, including the empty profile.
- profile_set creates or updates a string field; a null, empty or whitespace value deletes the key.

Keys are arbitrary nonempty strings, trimmed and compared case-insensitively. Values are trimmed strings. There are no predefined fields, default values, aliases, separate memories or dynamic tool schemas.

The UI is a simple editable Key / Value table with Add field, Delete, Save and Reload. Renaming a key replaces the old entry on save. Empty rows are ignored and duplicate keys are rejected.

## Durable Architecture And Constraints

The profile is a flat JSON object at UserData/user_profile.json using the existing storage-root resolver. The UI, CLI and child stdio process share the same path. Every operation reads the current file under a cross-process lock; mutations write a temporary file and atomically replace the destination. No personal values are logged.

On first read of a legacy document, retain a backup and migrate only stored values, not definitions, defaults or memories. Legacy flat maps remain readable.

Existing Saved Agent bindings migrate only unambiguous grants: prefs_get -> profile_get, prefs_get_all -> profile_get_all, prefs_set -> profile_set. Delete-only and memory-specific grants must not become write permission. CLI explicit tool permissions remain independent; no automatic system-prompt profile injection occurs.

## Non-Goals

No semantic search, typed fields, dynamic descriptions, conversation memory extraction, or new generic repository abstraction.

## Acceptance Criteria

- Exactly three tools with read-only metadata on reads.
- All profile fields are optional; missing and empty profile behave predictably.
- Empty values delete fields, and writes are idempotent.
- Legacy persisted values survive conversion with a backup.
- Save/reload across UI and stdio MCP processes persists data.
- Existing bindings do not gain more permissions during the upgrade.
- CLI only exposes the requested tools with explicit --allow-mcp grants.

## Verification

Unit tests cover normalization, persistence, migration, concurrent writers and validation. MCP stdio integration tests assert the three names, invocation, persistence and removal of obsolete tools. CLI and binding regression tests cover explicit read vs write grants and disabled mappings.
